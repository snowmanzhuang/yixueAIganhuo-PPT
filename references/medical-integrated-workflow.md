# Medical Integrated Workflow

This reference describes the single-skill workflow inside `yixueAIganhuo-PPT`.

## Core Principle

The parent agent only schedules and records state. 医学上游 worker, 页面生成 worker, and page worker perform the heavy work and return structured files.

Parent context budget: the parent stores routing decisions, task state, worker ids, artifact paths, validation summaries, and final report fields. Do not perform medical PPT planning in the parent thread. The parent must dispatch the 医学上游 worker before reading full source text and keeps structured artifacts only.

Do not ask the user to approve sub-agent spawning. Worker dispatch is part of this skill's execution contract; do not ask for a reply such as a permission phrase.

Before `FULL_AUTHORING_FROM_SOURCE` authoring starts, ask a concise preflight question block unless all required values are already known.

Before showing the block, start the bundled style selector server and use the printed `点击打开：...` URL as `{style_selector_url}`. Do not automatically open the browser; present the URL in the question block so the user can click it when needed:

```bash
python3 yixueAIganhuo-PPT/scripts/start-style-selector.py --background
```

If the local server cannot start, use the printed `本地文件兜底：...` file URL instead. The launcher resolves paths relative to its own script location, so it works after the whole skill folder is copied to another computer or installed under another username.

The block must start with: "请先回答下面几个问题："

Use numbered emoji labels:

```text
请先回答下面几个问题：

1️⃣ 页数：这次生成多少页 PPT？

2️⃣ 风格：请打开风格选择页，选 001-019 后回复序号。
{style_selector_url}
不选则默认：001 通用提示词风格。
```

If no PaddleOCR-VL token is detected, append:

```text
3️⃣ OCR：未检测到 PaddleOCR-VL token。
需要更准的文字识别，请打开这里获取 token：
https://aistudio.baidu.com/account/accessToken
然后回复 token；也可以回复“跳过”继续。
```

If a PaddleOCR-VL token is already detected, do not show the OCR prompt; ask only questions 1️⃣ and 2️⃣. The OCR token question is optional and must not block generation if the user skips it.

The page count remains a hard gate: ask the user for the target slide count unless the request already contains an explicit count. Do not default to any page count. Do not offer preset page-count choices. Store `target_slide_count_confirmed` and the numeric `TARGET_SLIDE_COUNT` in `task_state.json`.

The style selector is optional. If the user gives a valid selector (`001`-`019`, a matching style name fragment, or a style JSON filename/path), store it as `style_selector` and pass it to the upstream worker as `STYLE_SELECTOR`. If the user does not choose a style, store and pass `STYLE_SELECTOR=001`.

## Task Routing

The parent must classify intent before launching workers or creating an `editppt` run.

Use `scripts/classify-task-route.py` after quick inspection:

```bash
python yixueAIganhuo-PPT/scripts/classify-task-route.py \
  --user-request "<original user request>" \
  --input-summary "<brief first-page/overview/OCR/metadata notes>" \
  <input paths...>
```

The helper returns `task_route`, `should_start_with_editppt_prepare`, a reason, and an optional clarification question. The parent remains responsible for final judgment.

| Route | Input Meaning | Parent Action |
|---|---|---|
| `FULL_AUTHORING_FROM_SOURCE` | The inputs are source material for a new deck: medical paper PDF, research PDF, report, manuscript, guideline, Figure folder, table/chart image, screenshot evidence, or support document. | Run full upstream medical PPT authoring first. Generate new slide images, then convert those generated images through page workers. |
| `DIRECT_VISUAL_CONVERSION` | The inputs are an existing visual slide deck, exported image-only PPT, screenshot sequence, or already-designed page PDF that should be preserved as-is and made editable. | Skip upstream medical planning and run `editppt prepare <visual-input>` directly. |
| `AMBIGUOUS_INPUT` | Quick inspection cannot distinguish source material from an existing visual slide deck. | Ask one concise clarification, then set one of the two routes above. |

A medical paper PDF with title/authors/abstract/body/references is source material; do not start with `editppt prepare` on that PDF. Only direct visual conversion starts with `editppt prepare <visual-input>`.

## Full Authoring Hard Gate

For `FULL_AUTHORING_FROM_SOURCE`, the final PPTX is invalid unless:

1. Every `prompts/slideNN.txt` is a rich GPT Image 2 prompt and passes `scripts/validate-slide-prompt.py`.
2. Every `slides/slideNN.png` is generated by `editppt image generate/edit/batch`, not by local composition or a presentation authoring shortcut.
3. Every `slide_results/slideNN.json` has `status: "IMAGE_READY"`, `passed: true`, and `image_backend.tool_call` showing `editppt image generate/edit/batch`.
4. Every generated slide passes `scripts/validate-slide-ready.py` before `editppt prepare` or `editppt run add-page`.
5. Final assembly happens only after page-worker reconstruction, `editppt run record`, and `editppt run finalize`.

Do not use @oai/artifact-tool, python-pptx, HTML/SVG screenshots, local PIL composition, direct native PPT generation, legacy yixue scripts, or another PPTX writer as the final authoring path. If workers or image backend are unavailable, stop and report the blocker.

## Capability Split

| Capability | Owner | Output |
|---|---|---|
| Medical material understanding | 医学上游 worker | `source_inventory.json` |
| Figure inventory and filtering | 医学上游 worker | `figure_inventory.json` |
| Deck structure and speaker notes | 医学上游 worker | `plans/ppt_plan.json` |
| Per-slide prompt writing | 医学上游 worker | `prompts/slideNN.txt` |
| Full slide image generation | 页面生成 worker | `slides/slideNN.png`, `slide_results/slideNN.json` |

## Task Directory

Create a single task directory:

```text
output/yixueAIganhuo-PPT/<run_id>/
  assets/
  figures/
  plans/
  prompts/
  slides/
  slide_results/
  editppt_run/
  notes_manifest.json
  logs/
  reports/
  final/
  task_state.json
```

The parent stores only structured state:

- `task_state.json`: phase, per-slide status, worker ids, paths, retries, failure reasons, and concurrency slots.
- `plans/ppt_plan.json`: one slide entry per target slide.
- `prompts/slideNN.txt`: complete prompt written by the upstream worker.
- `slide_results/slideNN.json`: image generation result and backend provenance.
- `editppt_run/page_jobs.json`: page conversion state owned by `editppt`.

Do not put PDF full text, full OCR dumps, or page-level manifest details into parent context.

## Parent Workflow

1. Create the task directory and initialize `task_state.json`.
2. Inspect inputs, set `task_route`, and store it in `task_state.json`.
3. If `task_route` is `DIRECT_VISUAL_CONVERSION`, follow the Direct Visual Conversion Branch and skip upstream medical authoring.
4. Ask the concise preflight question block if needed. Start the style selector with `scripts/start-style-selector.py --background`, place the printed URL in the style question, do not auto-open the browser, confirm the target slide count, collect or default the style selector, and ask the OCR token question only when no PaddleOCR-VL token is detected. Do not default the page count and do not offer preset page-count choices. Set `target_slide_count_confirmed=true`, store `style_selector`, and pass `TARGET_SLIDE_COUNT` plus `STYLE_SELECTOR` to the upstream worker.
5. Dispatch one 医学上游 worker with source paths, user goal, confirmed target slide count, selected/defaulted style selector, and required output paths. The parent does not build the outline, speaker notes, or slide prompts itself.
6. Wait for upstream structured outputs: `source_inventory.json`, `figure_inventory.json`, `plans/ppt_plan.json`, and `prompts/slideNN.txt`.
7. Validate that `ppt_plan.json` has continuous `slide_id` / `slide_number` values, speaker notes, asset bindings, and prompt files.
8. Validate every generated prompt before image-worker dispatch:

```bash
python yixueAIganhuo-PPT/scripts/validate-slide-prompt.py \
  --prompt <task>/prompts/slideNN.txt \
  --slide-number <N>
```

Reject summary-style prompts. The prompt must contain expanded style-key text, slide plan content, concrete layout geometry, evidence/asset binding instructions, negative constraints, and continuity rules.

9. Configure or verify the unified image backend with `editppt setup`, `editppt doctor`, and optional `editppt config`.
10. Dispatch 页面生成 worker jobs:
   - slide 1 first.
   - slide 2 only after slide 1 image exists, with slide 1 as style reference.
   - slide 3+ only after slide 2 image exists, with slide 1 and slide 2 as style references.
11. Each 页面生成 worker must call `editppt image generate/edit/batch`; it must not call legacy image generation scripts or non-`editppt image` tools.
12. Before any generated slide image enters downstream conversion, run the preflight gate:

```bash
python yixueAIganhuo-PPT/scripts/validate-slide-ready.py \
  --slide <task>/slides/slide01.png \
  --result <task>/slide_results/slide01.json
```

Do not call `editppt prepare` until the preflight passes. The generated slide must have `slides/slideNN.png`, `slide_results/slideNN.json`, `status: "IMAGE_READY"`, `passed: true`, provenance from `editppt image generate/edit/batch`, 16:9 dimensions, and nonblank image content. Reject blank or white placeholder PNGs, pure-color or low-variance placeholders, synthetic `slides/sources/slideNN.png` files used only to initialize `editppt_run`, and hand-written page manifests against placeholder `source.png`.

13. As soon as the first generated page image passes preflight, create the downstream run:

```bash
editppt prepare <task>/slides/slide01.png --job-dir <task>/editppt_run
```

14. As later slide images finish, run the same preflight for each slide:

```bash
python yixueAIganhuo-PPT/scripts/validate-slide-ready.py \
  --slide <task>/slides/slideNN.png \
  --result <task>/slide_results/slideNN.json
```

15. Append only preflight-passed slides:

```bash
editppt run add-page <task>/editppt_run <task>/slides/slideNN.png --source-page <N>
```

16. Use the page-worker loop:
   - `editppt run next <run> --json`
   - `python yixueAIganhuo-PPT/scripts/build-page-worker-prompt.py <run> --page <page_id> --out <abs-page-dir>/worker-prompt.md`
   - spawn a real page worker with that prompt
   - `editppt run dispatch <run> --page <page_id> --agent-id <id> --prompt-file <abs-worker-prompt>`
   - after return, `editppt run record <run> --page <page_id> --agent-id <id>`
17. When all pages are recorded, run `editppt run finalize <run>`.
18. Report `editable_output`, `image_only_output`, validation result, notes status, warnings, and retries.

## Direct Visual Conversion Branch

Use this branch only for `DIRECT_VISUAL_CONVERSION`.

1. Create the downstream run from the existing visual input:

```bash
editppt prepare <visual-input> --job-dir <task>/editppt_run
```

2. Run the same page-worker loop used by the full authoring branch.
3. Finalize with `editppt run finalize <task>/editppt_run`.
4. Report `editable_output`, `image_only_output`, validation status, page count, warnings, and retries.

This branch is not for research/material PDFs. Those must first go through the Full Authoring Branch.

## Full Authoring Branch

The Full Authoring Branch is the default for medical source material. It includes upstream source understanding, Figure inventory, `ppt_plan.json`, speaker notes, slide prompts, generated slide images, `scripts/validate-slide-ready.py` preflight, incremental `editppt run add-page`, page-worker reconstruction, and finalization.

## Image Generation Worker Contract

Each 页面生成 worker owns one slide image. The worker receives:

- task directory
- slide id and slide number
- one slide entry from `ppt_plan.json`
- prompt file path
- required output path under `slides/`
- style reference slide image paths
- Figure asset paths bound to the slide
- image backend contract

Required behavior:

- Use `editppt image generate/edit/batch`.
- Use `editppt image edit` when the slide prompt includes source Figure inputs or style reference images.
- Write the final full-slide image to `slides/slideNN.png`.
- Write `slide_results/slideNN.json` with output path, dimensions, prompt path, reference images, figure inputs, backend command, start/end timestamps, and `passed`.
- Verify output dimensions are suitable for a 16:9 PowerPoint slide. Preferred canvas is `2560x1440`.
- Return only structured paths and status to the parent.

Forbidden behavior:

- No local PIL/HTML/SVG/python-pptx composition of a complete slide.
- No direct call to legacy image generation scripts.
- No non-`editppt image` generation tools.
- No silent downgrade to text-only or figure-free generation when the slide requires evidence images.

## Concurrency Policy

- The agent pool begins with the upstream planning worker; source understanding, Figure inventory, `ppt_plan.json`, speaker notes, and prompt writing are delegated there.
- Before any slide image exists, the parent may briefly allow more 页面生成 worker jobs when dependency rules permit them.
- After the first generated page image exists, slide-image generation concurrency is reduced to 2 or less.
- As soon as any generated slide image passes preflight, dispatch a page worker for that page immediately.
- The agent pool gradually reallocates worker slots to page workers as validated slide images accumulate.
- Reserve remaining worker capacity for downstream page workers.
- `editppt` page worker concurrency remains bounded by `page_jobs.json.max_concurrent_pages`.
- Never dispatch two workers for the same slide/page.
- Do not re-dispatch a failed page unchanged. Read its `validation.json` or `slide_results/slideNN.json`, fix the root cause, reset state, then dispatch a fresh worker.

## Structured Result Shapes

### `slide_results/slideNN.json`

```json
{
  "schema_version": 1,
  "slide_id": "slide01",
  "slide_number": 1,
  "status": "IMAGE_READY",
  "prompt": "prompts/slide01.txt",
  "output": "slides/slide01.png",
  "reference_images": [],
  "figure_inputs": [],
  "image_backend": {
    "tool_call": "editppt image generate/edit/batch",
    "model": "gpt-image-2"
  },
  "size_px": [2560, 1440],
  "passed": true,
  "warnings": []
}
```

### Page conversion result

The downstream page conversion result is `page_result.json` as defined in `references/manifest-schema.md`. The parent records only path, page id, worker id, validation status, hashes from `editppt run record`, and final accepted state.

## Failure Handling

- Upstream worker failure: read its structured error, fix missing input or schema problem, then re-dispatch once. Ask the user only for genuinely external missing items.
- Image generation worker failure: inspect `slide_results/slideNN.json` and command logs. Fix backend config, missing reference image, prompt path, or provider dimensions before retry.
- Page worker failure: follow the page-worker failure policy in the main `SKILL.md` and the `editppt run reset` policy. Do not hand-edit `page_jobs.json`.
- Finalization failure: treat `manifest.json` and `editppt` validation reports as authoritative. Fix failing page(s), reset/record/finalize again.

## Acceptance Checklist

- Parent received `ppt_plan.json` and did not keep long source text in context.
- Every slide image was produced through `editppt image generate/edit/batch`.
- Every ready slide entered conversion scheduling as soon as practical.
- Every page conversion reached `recorded` through `editppt run record`.
- Final editable PPTX and final image-only PPTX were built through `editppt run finalize`.
- Both decks consume `notes_manifest.json` for speaker notes when available.
- The final report includes `editable_output`, `image_only_output`, validation result, page count, speaker notes status, warnings, and any failed/retried pages.
